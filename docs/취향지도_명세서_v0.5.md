# 취향 지도 (가칭) — 제품 명세서

**버전** v0.5 · **갱신일** 2026.09.03 · **이전 버전** v0.4
**성격** 구현 명세. 시장 조사·논거·설득 내용은 v0.1에 보존되어 있으며 본 문서에서 제외한다.
**개발 방식** 바이브 코딩 — AI 코딩 도구가 코드를 전부 작성하고, 두 개발자는 지시(Linear 이슈 체크리스트)·검수(배포 URL에서 완료 조건 확인)·결정을 담당한다. 상세는 결정 기록 U4·U5 참조.

## 1. 제품 정의

매체를 구분하지 않고 감상 기록을 수집하는 서비스. 최종 지향은 기록을 **좌표 공간 위의 탐험 가능한 지도**로 시각화하는 것이나, 이는 v2 단계 목표다(§4.8).

**제품 성격**: 기록 앱이 아닌 **수집 게임**. 유저 0명일 때도 단독으로 작동해야 한다.

**단계별 핵심 명제**
- *초기*: 감상 기록 → 세트 달성률·배지 → 미완성 항목 노출 → 감상 동기
- *v2 이후*: 감상 기록 → 좌표 → 타일 점등 → 안개 영역 노출 → 감상 동기. 좌표 근접도가 곧 추천 알고리즘이 되어 별도 추천 엔진이 불필요해진다.

## 3. 도메인 모델

### 3.1 작품 동일성 규칙 (D5)

**원칙: 콘텐츠가 다르면 별개 작품, 언어만 다르면 동일 작품.**

| 케이스 | 처리 | 비고 |
|---|---|---|
| 시리즈의 시즌 | **별개 작품** | 시즌 1 / 시즌 2는 각각 독립 레코드 |
| 리마스터판 | **별개 작품** | 원본과 분리 |
| 감독판 / 확장판 | **별개 작품** | 극장판과 분리 |
| 더빙 / 자막 / 현지화 제목 | **동일 작품** | 언어 차이는 동일성에 영향 없음 |
| 게임의 DLC | **별개 작품** | 본편과 분리 |
| 게임 리마스터·리메이크 | **별개 작품** | 리마스터 규칙과 동일 |
| 플랫폼 차이 (PC/PS/Switch) | **동일 작품** | 언어 차이와 같은 층위로 취급 |

**⚠ 확장 적용 필요 — 미확정 항목**
"번역판"의 원래 논점은 도서의 **다른 번역가·출판사 판본**이었다. 위 원칙(언어 차이는 동일 작품)을 그대로 적용하면 **동일 작품**이 되지만, 도서는 ISBN이 판본마다 다르므로 다음이 필요하다.

- 원작 단위 `Work`와 판본 단위 `Edition`을 분리하고, 기록은 `Work`에 붙인다.
- `Edition`은 표시·바코드 스캔용 메타데이터로만 사용한다.

→ **§10 미결정 항목 U1로 이관.** 책 도입(v1) 전까지 확정 필요.

### 3.2 엔티티 구조

```
Work (작품)
├─ id
├─ media_type      : game | movie | tv | book | custom
├─ canonical_title
├─ title_ko        : 한국어 제목 (수동 매핑 테이블 병행)
├─ release_year
├─ external_ids    : { igdb, steam_appid, tmdb, isbn, ... }
├─ parent_work_id  : 시즌·DLC의 상위 작품 (nullable, 표시 그룹핑용)
├─ source          : official | user_created
└─ verified        : bool (user_created의 검수 여부)

Record (기록)
├─ id
├─ user_id
├─ work_id
├─ status         : completed | in_progress | dropped | backlog
├─ coordinates    : [{ map_id, x, y }]
├─ dropped_at     : 이탈 지점 (dropped 전용, 텍스트/수치)
├─ progress       : 진행 지점 (in_progress 전용)
├─ replay_count   : 재감상 횟수
├─ consumed_at    : 감상 일자
├─ note           : 감상문 (nullable)
├─ visibility     : private (기본) | public
└─ import_source  : manual | steam | csv | screenshot | ...
```

**설계 주석**
- `parent_work_id`는 동일성 판단에 사용하지 않는다. 시즌은 별개 작품이며, 이 필드는 UI 그룹핑 전용이다.
- `coordinates`는 **v2에서 사용을 시작한다**(§4.8). 그때 마이그레이션이 발생하지 않도록 스키마에는 미리 포함하고, 그전까지는 빈 배열로 유지한다. 배열인 이유는 지도 다중화를 대비한 것이다.

### 3.3 매체별 DB 소스

| 매체 | 1차 소스 | 보조 | 릴리스 |
|---|---|---|---|
| **게임** | IGDB | Steam Web API (자동 입력) | MVP |
| **영화** | TMDB | KMDb (한국 영화 메타데이터) | MVP |
| **드라마·TV** | TMDB | — | MVP |
| 책 | 알라딘 API | 국립중앙도서관 | v1 |
| 애니 | AniList | MyAnimeList | v2 |
| **웹툰** | 없음 | 유저 등록(§3.4)으로 대체 | v2+ |

**한국어 메타데이터**: TMDB·IGDB는 한국어 제목이 비거나 부정확한 경우가 많다(특히 인디 게임). 자체 매핑 테이블을 운영하며, 유저 제보 경로를 v1에 포함한다.

### 3.4 유저 직접 등록 (D3)

DB를 제공하지 않는 매체(웹툰, 공연, 유튜브 채널, 인디 작품 등)를 유저가 직접 등록한다.

**필수 입력**: 제목, 매체 유형, (선택) 연도·제작자·URL·커버 이미지

**규칙**
- `source = user_created`, `verified = false`로 생성한다.
- 동일 매체 내 제목 유사도 검사로 중복 생성을 방지하고, 유사 항목이 있으면 기존 것을 제안한다.
- 일정 수 이상의 유저가 같은 작품을 기록하면 검수 큐에 올려 `verified` 승격을 검토한다.

**희귀도와의 관계 (D6)**
유저 직접 등록은 희귀도 어뷰징 경로가 될 수 있으므로, **`source = user_created` 작품에는 희귀도를 부여하지 않는다.** 해당 매체의 공식 DB가 확보되는 시점에 희귀도 대상으로 편입한다. 상세는 §4.6.

## 4. 핵심 메커니즘 명세

> **당장 구현하지 않음.** 본 장은 방향 기록용이며, 구현 시점에 별도 상세 명세를 작성한다.

### 4.1 도입 순서

| 단계 | 메커니즘 | 명세 |
|---|---|---|
| **초기** | 컬렉션 세트 / 리절트 / '안 본 것' 기록 / 희귀도 / 주간 던전 / 스크린샷 입력 | §4.2~§4.7 (상세) |
| **후기** | **감정 좌표계 / 지도** / 취향 DNA / 사람 수집 / 클러스터 명명 / 비동기 룸 / B2B | §4.8 (개요만) |

감정 좌표계와 지도는 제품의 최종 지향점이나 도입 시점이 뒤로 이동했다. 상세 설계는 도입 단계에서 별도 문서로 작성한다.

### 4.2 컬렉션 세트

**구조**: 세트 = 작품 목록 + 이름 + 설명. 완성 시 배지 부여.

```
Set
├─ id, name, description
├─ creator_id (null = 공식)
├─ work_ids[]
├─ badge_asset
└─ is_public
```

**생성 주체**: 운영자 / 유저 둘 다. **유저 세트가 핵심이다.** 운영자만 만들면 확장성이 없고, 유저 세트는 공유 링크를 갖고 그것이 유입 경로가 된다.

**진행 표시**: 세트별 달성률(n/m)을 상시 노출한다. 초기 단계에서 **지도를 대신해 "빈칸을 채우는" 동기를 담당하는 유일한 장치**이므로, 미달성 항목의 시각적 존재감을 강하게 설계한다.

### 4.3 월간/연간 리절트

**형식**: 인포그래픽이 아닌 RPG 리절트 창.

**표시 항목**
- 매체별 시간·개수 배분 (통합 서비스만 가능한 화면)
- 완주율·중도하차율
- MVP 작품 (최고 별점 또는 재감상 최다)
- 획득 배지·세트 달성
- 희귀도 상위 기록
- *(지도 도입 후)* 신규 점등 타일 수 / 개방률

**주기**: 월간이 기본, 연간은 확장판.
**출력**: 공유용 이미지 자동 생성(§6.3). 초기 단계의 유일한 바이럴 장치다.

### 4.4 '안 본 것' 기록

**대상 상태**: `dropped` (중도하차), `backlog` (예정)

**입력 규격**
- `dropped`: 이탈 지점만 받는다 (예: "3화", "40%", "2시간"). **평가·좌표를 요구하지 않는다.** 끝까지 안 본 작품에 점수를 매기라는 요구는 심리적 저항이 크고, 이탈 지점 자체가 충분히 강한 신호다.
- `backlog`: 평가 없음. 위시리스트와 동일 취급.

**활용**: 주간 던전 퀘스트 소스(§4.5), 완주율 통계(§4.3).

### 4.5 주간 던전

**동작**: 매주 3개 조건을 제시하고, 조건에 맞는 작품을 감상·기록하면 클리어. 보상은 배지와 리절트 반영.

**퀘스트 소스 우선순위**
1. 유저의 `dropped` 기록 → "3화에서 접은 그것"
2. 유저의 `backlog` 기록 → "사놓고 안 한 것"
3. 미보유 세트 항목 → "세트 완성까지 2개"
4. *(지도 도입 후)* 안개 타일 → "미개척 영역"

**선행 조건**: §4.4가 먼저 구현되어야 1·2번이 작동한다. 3번은 세트만으로 성립하므로 지도 없이도 던전은 완결된다.

### 4.6 희귀도

**산정**: 전체 유저 중 해당 작품을 기록한 비율.

**적용 범위 (확정 D6)**
- **공식 DB에 등록된 매체의 작품에만 부여한다.**
- `source = user_created` 작품은 산정에서 제외한다.
- **해당 매체의 공식 DB가 추가되는 시점에, 그 매체의 작품을 희귀도 대상으로 편입한다.** (예: 웹툰 DB 확보 시 웹툰 작품이 희귀도 대상이 됨)
- 편입 시 기존 `user_created` 레코드는 공식 DB 항목으로 병합한 뒤 산정에 포함한다.

**운영 규칙**
- 희귀도는 **라벨로만 사용하고 직접 보상에 연결하지 않는다.** 보상과 연결하면 "인기작 기록은 손해"라는 인식이 생겨 데이터가 롱테일로 편향된다.
- 초기에는 전체 작품이 레어로 표시되므로, **최소 유저 수 도달 전까지 비활성화**한다.

### 4.7 스크린샷 입력

**동작**: 이미지 업로드 → OCR + 비전으로 제목 후보 추출 → 작품 매칭(§5.3) → 유저 확인.

**위치**: 공식 API가 있는 매체(게임·영화)는 API를 우선한다. 스크린샷은 API가 없는 영역의 보완재다.

**한계**: 정확도가 낮으므로 항상 유저 확인 단계를 거친다. 자동 확정하지 않는다.

### 4.8 후기 메커니즘 (개요)

도입 시점이 뒤이므로 개요만 기록한다. 상세 명세는 각 도입 단계에서 작성한다.

| 메커니즘 | 개요 | 선행 조건 |
|---|---|---|
| **감정 좌표계** | 작품 기록 시 2축 평면에 점을 찍어 매체 간 비교 가능한 척도를 확보. 별점과 병존하며 별점은 "얼마나 좋았나", 좌표는 "어떤 작품인가"를 담당 | 축 정의(U2) 확정 |
| **지도** | 좌표 평면을 육각 타일로 분할. 기록 없는 타일은 안개로 표시하고, 타일 탭 시 해당 영역 작품 추천. **좌표 근접도가 곧 추천 알고리즘**이므로 별도 추천 엔진이 불필요 | 좌표계 + 타일 밀도(U3) |
| 취향 DNA | 기록을 문자열로 압축해 프로필 노출, 유저 간 유사도 비교 | 좌표 데이터 축적 |
| 사람 수집 | 취향이 통하는 사람을 카드로 수집. 카드 스펙란 = DNA | DNA + 유저 규모 |
| 클러스터 명명 | 축적된 좌표 군집에 사후적으로 이름 부여 (= 취향축) | 좌표 데이터 축적 |
| 비동기 감상 룸 | "지난 7일간 이 작품을 본 사람들의 한 줄"을 모아두는 공간 | 유저 규모 |
| 데이터 B2B | 취향축 데이터를 출판사·게임사에 판매 | 유저 수만 명 + 동의 구조 |

**실시간 감상 룸은 채택하지 않는다.** 동시 접속 규모가 전제이며 빈 방은 죽은 앱처럼 보인다. 비동기 버전으로 대체한다.

**스키마 대비**: `Record.coordinates`는 좌표계 도입 전까지 빈 배열로 유지한다. 도입 시 마이그레이션이 발생하지 않도록 스키마에는 미리 포함해 둔다(§3.2).


## 5. 가져오기 명세

### 5.1 원칙

가져오기는 상대 서비스의 협조를 필요로 하지 않는다. 데이터를 옮기는 주체는 **유저 본인**이다.

**서버에서 타 서비스를 직접 스크래핑하지 않는다.** 이용약관 위반이며 법적 리스크가 있다. 이 선은 넘지 않는다.

### 5.2 경로별 명세

| 우선 | 경로 | 대상 | 구현 | 릴리스 |
|---|---|---|---|---|
| 1 | **Steam Web API** | 게임 | SteamID → 보유 게임·플레이 시간·도전과제. 정확도 100% | MVP |
| 2 | **CSV 업로드** | 영화 | Letterboxd 공식 내보내기 파일 파싱. Goodreads는 파서만 두고 v1(책 도입) 시 활성화 — T20에서 확정 | MVP |
| 3 | **왓챠피디아 CSV** | 영화·드라마·책 | 유저가 외부 도구로 추출한 파일 수용 | v1 |
| 4 | **텍스트 붙여넣기** | 전체 | 제목 목록 일괄 입력 → 매칭 | v1 |
| 5 | 스크린샷 | 전체 | §4.8 | v1 |

**왓챠피디아 관련 정책**
- 왓챠피디아는 공식 백업 기능·공개 API를 제공하지 않는다.
- 유저 커뮤니티가 만든 추출 도구(브라우저 스크립트, `watchapedia-export` 등)가 존재하며, 이는 유저 브라우저에서 유저 본인 세션으로 동작한다.
- **우리는 추출 도구를 배포하지 않는다.** 앱에는 "추출한 파일을 여기 올리세요" 수용 기능만 구현하고, 도구는 외부 링크로 안내한다. 리스크를 최소화한다.

**법적 배경 (참고)**: 개인정보 전송요구권(전 분야 마이데이터)이 2025.3 시행되었으나 대상 사업자 규모 요건과 분야별 순차 시행으로 현시점에는 적용되지 않는다. 3~5년 내 표준화를 전제로 설계한다.

### 5.3 작품 매칭 규격

**가져오기의 실질적 난이도는 파싱이 아니라 매칭이다.**

**매칭 키 우선순위**
1. 외부 ID 직접 대응 (steam_appid, tmdb_id, isbn) → 즉시 확정
2. 제목(정규화) + 연도 완전 일치 → 자동 확정
3. 제목 유사도 + 연도 ±1 → 후보 제시
4. 미발견 → 스킵 목록

**제목 정규화 규칙**
- 대소문자 통일, 특수문자·공백 제거
- 한국어/영어 제목 교차 대조 (매핑 테이블 참조)
- 부제·시즌 표기 분리 (`종이의 집 파트4` → 본제 + 시즌 토큰)

**UX 규격**
- 자동 확정 건은 바로 반영, 유저에게 결과만 통보
- 애매 건은 **후보 3개 제시 → 탭 1회로 선택**
- 미발견 건은 스킵 목록에 모아 일괄 표시, 유저 직접 등록(§3.4)으로 연결

> **목표 지표: 500건 중 450건 자동 확정, 50건 수동.** 100% 자동은 목표로 하지 않는다.

**가져온 기록의 초기 상태**
- `status = completed`, `coordinates = []` (미분류)
- 일괄 좌표 지정 UI(§4.1)로 유도한다.

## 12. ~~미해결 위험~~ 해결됨 — MVP 차별점 (U8)

> **✅ 해결 (2026.09.03)**: 선택지 ① 채택 — Steam 연동 + RPG 리절트·공유 이미지에 집중한 경량 MVP. 해당 이슈(Linear WEB-19·23·24)에 품질 기준 '가장 높음' 표기. 근거·완화책·재검토 조건은 **결정 기록 U8** 참조. 아래는 결정 당시의 문제 정의 원문이다.

좌표계와 지도가 v2로 이동하면서, MVP의 기능 목록이 기존 통합 기록 앱과 사실상 동일해졌다.

**현재 MVP 구성**: 기록 + 가져오기 + 세트/배지 + 리절트

이 조합은 v0.1 §3.2에서 조사한 OnTrack(매체 8종 + 업적 + 컬렉션 + 가져오기, 평점 4.9, **Android 누적 2,300 DL**)과 기능적으로 겹친다. 해당 조사의 결론은 "기능 완성도와 규모는 비례하지 않는다"였다.

**MVP 단계에서 남아 있는 차별 요소는 두 가지뿐이다.**

1. **Steam 연동으로 게임을 1급 매체로 다루는 것** — 조사한 국내 서비스 중 게임을 제대로 다루는 곳이 없었고, 게임은 유일하게 공개 API로 입력 비용이 0인 매체다.
2. **RPG 리절트 형식의 결산 + 공유 이미지** — 바이럴 장치.

**결정 필요**: MVP를 이 두 가지에 집중시켜 "게임까지 포함하는 기록 앱"으로 낼 것인가, 아니면 좌표계·지도의 축소판(예: 지도 1장, 축 2개 고정)을 MVP에 포함시켜 차별점을 앞당길 것인가.
